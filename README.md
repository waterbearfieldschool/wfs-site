# Waterbear Field School site (Eleventy)

Static site for [waterbearfieldschool.org](https://waterbearfieldschool.org), built with Eleventy and deployed to GitHub Pages.

## Setup on a new machine

Cloning the repo isn't quite enough — a few host-specific steps. There's a
one-shot helper: after cloning, run **`./scripts/setup.sh`** (does steps 2–3
and checks the rest). Or do it by hand:

```bash
# 1. Clone (SSH — you need push access to the waterbearfieldschool org).
#    Clone to ~/gitwork/wfs-site specifically: the wfs-edit wrapper hardcodes
#    that path, so wfs-edit pull/push/status only work from there.
mkdir -p ~/gitwork && git clone git@github.com:waterbearfieldschool/wfs-site.git ~/gitwork/wfs-site
cd ~/gitwork/wfs-site

# 2. Check out the active working branch (NOT main)
git checkout foundations-restructure

# 3. Install deps (any recent Node; the Pi runs Node 24, no strict pin)
npm install

# 4. Symlink the wfs-edit wrapper so serve.sh / deploy.sh work
ln -sf "$(pwd)/scripts/wfs-edit" ~/.local/bin/wfs-edit    # ensure ~/.local/bin is on PATH
```

Then `./serve.sh` starts the dev server at http://localhost:8080.

**No secrets to copy** — there's no tracked `.env`, and the Snipcart key in
`src/_data/site.json` is the *public* key.

### Also required if you'll **deploy** (not just edit)

`deploy.sh` publishes by copying `_site/` into the GitHub Pages repo and
force-pushing it. That repo must exist as a **sibling directory**, or the
deploy bails:

```bash
# clone it NEXT TO wfs-site (i.e. ../waterbearfieldschool.github.io)
git clone git@github.com:waterbearfieldschool/waterbearfieldschool.github.io.git
```

### ⚠️ Multi-device discipline

Both the laptop and the Pi (iris) edit this repo — the Pi also commits via
Telegram-driven edits. To avoid divergence:

- Let `./serve.sh` (or `wfs-edit pull`) sync **before** you start editing.
- Run `wfs-edit push "<msg>"` when you're done so the other device sees it.
- The deploy **force-pushes** the Pages repo — only deploy from one place at a time.

## Daily workflow

The two-script workflow handles syncing, editing, and deploying. Both scripts
respect the multi-device case (laptop + Pi) by pulling from origin where safe
and using the `wfs-edit` wrapper for guarded commits/pushes.

### Develop

```bash
./serve.sh
```

Fast-forwards from origin if safe (working tree clean), then starts the local
dev server at [http://localhost:8080](http://localhost:8080) with hot reload.

### Push edits without deploying

```bash
wfs-edit push "<commit message>"
```

For when you're done editing on one device and want the other device to see
the changes, without yet redeploying the live site. Auto-rebases on push
reject if origin moved during your edit window.

### Deploy

```bash
./deploy.sh "<commit message>"
```

Commits + pushes any pending source changes via `wfs-edit`, runs a fresh
build, copies `_site/` into the Pages repo, and force-pushes. Defaults to
the message `update` if you omit it (back-compat, but please supply a real
message — your git log will thank you).

### Status

```bash
wfs-edit status
```

Shows current branch, ahead/behind, and working-tree state.

## Local tooling

`wfs-edit` lives in this repo at `scripts/wfs-edit` and is symlinked into
`~/.local/bin/wfs-edit` on each device. That way the canonical script
travels with the repo. On a fresh checkout, set up the symlink with:

```bash
ln -s "$(pwd)/scripts/wfs-edit" ~/.local/bin/wfs-edit
```

(or add `scripts/` to your PATH).

## Customize

- Edit `src/_data/site.json` for name, tagline, links.
- Write posts in `src/writing/` and projects in `src/projects/`.
- Adjust layout CSS in `src/assets/css/site.css`.

## What's gitignored

- `_site/` — build output (regenerated by `npm run build`)
- `node_modules/` — dependencies (regenerated by `npm install`)
- `.DS_Store`, `.env`, swap files

The build output and dependencies live on disk but aren't tracked. This keeps
the source repo small and avoids the dirty-working-tree problems that come
from committing regenerable artifacts.
